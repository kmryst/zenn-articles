## はじめに

Zenn の記事を書きたい気持ちはあっても、実装と執筆が分断されると、あとから書くのが急に重くなります。

実装中は、

- どこで詰まったか
- 何を疑ったか
- どの案を捨てたか
- なぜその構成に戻したか

を覚えています。

でも、デプロイが終わって数日経つと、コードは残っていても判断の温度が消えます。結果として、「いつか記事にしよう」と思ったまま下書きにもならないことがあります。

そこで、実装用リポジトリと Zenn 用リポジトリを同じワークスペースに置き、実装しながら記事を書ける形にしました。

この記事では、Zenn と GitHub の基本的な連携手順そのものよりも、**実装中の知見を逃さず記事にするためのローカル環境と運用**について書きます。

対象読者は、Zenn の GitHub 連携や Zenn CLI を使いながら、実装ログやトラブルシュートを記事にしたい人です。

## 先に結論

いまは、次のような構成で作業しています。

```text
~/dev/projects/
├── app-repository/  # 実装用リポジトリ
└── zenn-articles/   # Zenn記事用リポジトリ
    ├── articles/
    ├── books/
    ├── docs/
    ├── package.json
    └── README.md
```

ポイントは、実装リポジトリと記事リポジトリを混ぜないことです。

- 実装コードは実装用リポジトリで管理する
- Zenn 原稿は Zenn 用リポジトリで管理する
- ただし、エディタや AI エージェントからは同じ作業文脈で見えるようにする

モノレポにするのではなく、リポジトリは分けたまま、作業場だけ近づけています。

## なぜ同じワークスペースに置くのか

技術記事の価値は、完成形の説明だけではなく、途中の判断に出やすいと思っています。

たとえば、前に書いた RDS と Terraform の記事では、最終的な構成だけでなく、

- RDS 管理シークレットを本命にした
- Permission Boundary で apply が止まった
- 一度 Terraform 管理 Secret に撤退した
- ただし恒久策にはしなかった
- 権限を直してから本命構成に戻した

という流れを書きました。

この手の内容は、実装中なら書けます。けれど、後日あらためて記事を書こうとすると、何を疑って、どこで切り分けて、なぜ撤退したのかが薄れていきます。

なので、記事を書く環境を「実装が終わったあとに開く場所」ではなく、「実装中に横に置いておく場所」にしました。

## 選ばなかった構成

最初に、選ばなかった構成を整理しておきます。

### 実装リポジトリの中に記事を置く

これは選びませんでした。

アプリケーションのコードと記事原稿を同じリポジトリに入れると、管理は一見楽になります。ただ、Zenn と GitHub 連携するリポジトリとしては、`articles` や `books` を素直に置いた専用リポジトリのほうが扱いやすいです。

また、記事の変更とアプリケーションの変更が同じ履歴に混ざると、あとから見たときに意図が追いにくくなります。

### Zenn の Web エディタだけで書く

これも選びませんでした。

Web エディタで完結できるのは便利ですが、実装中のコード、Terraform の差分、GitHub Actions のログ、記事の下書きを横断しながら書きたい場合は、ローカルのほうが楽でした。

特に、記事に載せるコマンド例やエラーログを確認しながら書くなら、実装リポジトリの隣に記事リポジトリがあるほうが切り替えが少なくなります。

### 記事用リポジトリだけを別で開く

これも悪くはありません。

ただ、自分の場合は「実装」と「執筆」を別作業として分けると、記事を書くタイミングを逃しがちでした。

そのため、リポジトリは分けつつ、ワークスペースとしては近くに置く形にしました。

## セットアップ

Zenn CLI は、ローカルで記事の作成やプレビューができる Zenn 公式の CLI ツールです。基本的な導入や GitHub 連携は公式ドキュメントにまとまっているので、ここでは自分の作業環境として必要だった部分だけを書きます。

:::message
[Zenn CLIで記事・本を管理する方法](https://zenn.dev/zenn/articles/zenn-cli-guide)
:::

まず、作業用ディレクトリの下に、実装用リポジトリと記事用リポジトリを並べます。

```bash
mkdir -p ~/dev/projects
cd ~/dev/projects

git clone git@github.com:your-name/app-repository.git
git clone git@github.com:your-name/zenn-articles.git
```

今回の例では、次のようになります。

```text
~/dev/projects/
├── app-repository/
└── zenn-articles/
```

Zenn 用リポジトリでは、Zenn CLI を使えるようにしておきます。

```bash
cd ~/dev/projects/zenn-articles
npm install
npm run zenn:preview
```

`package.json` には、最低限これくらいの script を置いています。

```json
{
  "scripts": {
    "zenn:preview": "zenn preview",
    "article:new": "zenn new:article",
    "book:new": "zenn new:book"
  }
}
```

公式ドキュメントでは `npx zenn preview` が紹介されていますが、毎回打つコマンドを短くしたいので `npm run zenn:preview` に寄せています。

## ワークスペースとして開く

VS Code のマルチルートワークスペース機能を使えば、2つのリポジトリを同じワークスペースに追加できます。

:::message
マルチルートワークスペースの詳細は、VS Code 公式ドキュメントを参照してください。
[Multi-root Workspaces](https://code.visualstudio.com/docs/editor/multi-root-workspaces)
:::

:::details .code-workspace の設定例
`.code-workspace` を使うなら、たとえばこんな形です。

```json
{
  "folders": [
    {
      "name": "app-repository",
      "path": "app-repository"
    },
    {
      "name": "zenn-articles",
      "path": "zenn-articles"
    }
  ]
}
```

実際には `.code-workspace` ファイルを作らなくても、エディタ上で複数フォルダを開ければ十分です。
:::

大事なのは、実装中に次のような移動がすぐできることです。

- 実装差分を見る
- エラーログを見る
- 記事の下書きに判断を書く
- Zenn preview で表示を確認する
- 必要なら記事だけ別コミットで push する

## 記事を書くためのメモもリポジトリに置く

Zenn 用リポジトリには、記事そのものだけでなく、執筆用のメモも置くことにしました。

```text
zenn-articles/
├── articles/
├── books/
└── docs/
    └── writing-guide.md
```

`docs/writing-guide.md` には、記事を書くときの基準を残しています。

たとえば、次のような観点です。

- 完成形の正解だけでなく、どこで詰まったかを書く
- 選ばなかった選択肢と、その理由を書く
- 一時的な workaround と恒久策を混ぜない
- 初出の専門用語は一言で定義する
- コード例だけでなく、診断や復旧コマンドも入れる

これは公開記事ではなく、自分用の執筆ガイドです。

毎回ゼロから「良い記事とは何か」を考え直すのではなく、前回うまくいった型を次の記事にも使えるようにしています。

## 実装中の流れ

実際の流れは、だいたい次のようになります。

1. 実装用リポジトリで作業する
2. 詰まったら、エラーや仮説を短くメモする
3. 解決したら、採用した案と捨てた案を書く
4. Zenn 用リポジトリの `articles/` に下書きを作る
5. `npm run zenn:preview` で読みながら整える
6. `published: false` のままコミットしておく
7. 公開できる状態になったら `published: true` にして push する

ここで重要なのは、最初からきれいな記事を書こうとしないことです。

実装中に残すべきなのは、完成した文章ではなく、あとで記事の芯になる材料です。

特に残しておきたいのは、次の3つです。

- どこで詰まったか
- 何を捨てたか
- なぜ捨てたか

この3つが残っていると、あとから記事にするときにかなり楽になります。

## AI に手伝ってもらう前提でも相性がいい

自分の場合、記事の構成整理や文章化は AI にかなり手伝ってもらっています。

そのとき、実装リポジトリと記事リポジトリが同じ作業場にあると、説明が楽になります。

- この実装差分を見てほしい
- このエラーの流れを記事にしたい
- この記事の下書きを、実装内容と矛盾しないように整えたい
- 公開前に、捨てた選択肢と理由が書けているか見てほしい

こういう依頼がしやすくなります。

記事用リポジトリだけを見ていると、文章は整っても、実装時の文脈が抜けることがあります。逆に実装リポジトリだけを見ていると、記事としての構成が弱くなることがあります。

両方を同じワークスペースに置くと、その間を行き来しやすくなります。

ただし、AI に任せれば記事の価値が自動的に生まれるわけではありません。自動化できるのは、メモを整えることや文章のたたき台を作ることまでです。読者にとって価値になるのは、どの条件で詰まり、何を比較し、なぜその選択をしたのかという判断材料です。

そのため、この環境で目指しているのは記事の量産ではなく、実装中の判断を読者が使える形に変換しやすくすることです。

## この構成の注意点

便利ですが、注意点もあります。

まず、リポジトリが2つあるので、どちらの作業ツリーに変更があるかを意識する必要があります。

```bash
git -C ~/dev/projects/app-repository status
git -C ~/dev/projects/zenn-articles status
```

実装のコミットと記事のコミットは、基本的に分けたほうが見通しが良いです。

:::message alert
記事に載せる情報にも注意が必要です。実装リポジトリのログや Terraform 差分を見ながら書けるぶん、アカウント ID、シークレット、内部情報をうっかり載せないようにします。
:::

公開前には、少なくとも次を確認します。

- シークレットやトークンを書いていないか
- AWS アカウント ID などを必要以上に出していないか
- 内部向けの固有名詞を出しすぎていないか
- 暫定策を推奨構成のように書いていないか
- `published: true` にする前に preview で読んだか

## 今後の改善

この構成で運用を始めてまだ日が浅いため、改善したい点も残っています。

- **記事テンプレートの整備**: `zenn new:article` で生成される空の Markdown に、構成の骨格（先に結論・選ばなかった構成・今後の改善など）を自動で入れる仕組みを用意したい
- **writing-guide.md と AI の連携**: 執筆ガイドを Cursor Rules として登録し、AI にレビューを依頼するときに自動で参照させるようにしたい
- **公開前チェックの自動化**: シークレットの混入検知やフロントマターの必須項目チェックを、Git hook や CI で実行できるようにしたい

## まとめ

Zenn と GitHub を連携すると、記事を Git で管理できます。

ただ、自分にとって大きかったのは、単に Markdown を GitHub で管理できることではありませんでした。

実装用リポジトリと Zenn 用リポジトリを同じワークスペースに置いたことで、実装中の判断を記事に変えやすくなりました。

- コードと記事は別リポジトリで管理する
- でも作業場としては近くに置く
- 実装中の「詰まった点」「撤退」「捨てた理由」を逃さない
- 記事の型は `docs/writing-guide.md` に残して再利用する

この形にしてから、記事を書く作業が「実装後に頑張る別作業」ではなく、「実装の延長」に近くなりました。

記事テンプレートの整備や公開前チェックの自動化など、まだ手をつけていない部分もありますが、まずは「実装と執筆の距離を縮める」だけでも書きやすさは大きく変わります。

技術記事を書きたいけれど、実装と執筆が分断されてなかなか書けない人には、リポジトリを分けたまま同じワークスペースに置く運用はおすすめです。
