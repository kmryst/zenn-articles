## はじめに

AI Agent を開発フローに入れると、運用ルールを明文化したくなります。

Issue の作り方、PR の書き方、ラベルの付け方、Terraform や GitHub Actions を触る時の注意点。これらを `CONTRIBUTING.md` や Agent 向けの指示ファイルに書いておくと、毎回長いプロンプトを書かなくても、ある程度まともに動いてくれます。

ただし、ここには罠があります。

AI に運用設計を相談すると、かなりの確率で「項目を増やす」「チェックを増やす」「テンプレートを厚くする」方向へ進みます。安全側に倒しているように見えますが、実際には日常運用の摩擦が増え、守られないルールになりがちです。

この記事では、AI Agent と一緒に GitHub 運用を整える中で、あえて **Issue 本文に新しい項目を追加しなかった** 判断について書きます。

ここでいう「No」は、AI を使わないという意味ではありません。AI が出してきた安全側の提案をそのまま採用せず、運用コストと失敗時の影響を見て、人間が設計判断を返すという意味です。

対象読者は、GitHub Issues / Pull Requests / GitHub Actions を使って開発フローを回していて、Claude Code や Codex のような AI Agent からも同じ運用ルールで Issue / PR を扱えるようにしたい人です。特に、運用ルールを整えたいが、Issue テンプレートやチェック項目を増やしすぎたくない人向けです。

:::message
この記事は、個人開発または少人数運用の `dev` 中心リポジトリを前提にしています。
厳格な本番変更管理、複数チームの承認フロー、監査証跡が必須の環境では、より強いプロセスが必要になる場合があります。
:::

## 先に結論

最終的に採った方針は、次の通りです。

- Issue 本文には `運用区分` のような新項目を追加しない
- Issue 起票前プランと PR 作成前プランで、軽運用 / 厳密運用を判定する
- 判定基準の正本は `CONTRIBUTING.md` に集約する
- `docs/operations/github-flow-guardrails.md` には、なぜ Issue 本文項目を増やさないかの理由と未採用案を書く
- `CLAUDE.md` には、Claude Code がその方針を読むための入口を書く
- Issue テンプレート、Issue Form、workflow、helper script は今回は変更しない

つまり、判断は増やしましたが、入力欄は増やしていません。

ここでいう **起票前プラン** とは、AI Agent に Issue を作らせる前に、「この内容で Issue を作ります」という下書きと、ラベル案、軽運用 / 厳密運用の判定、その理由を提示させ、人間が確認する段階のことです。

変更前後を短く書くと、こうです。

| 観点 | 変更前に考えた案 | 実際に採用した形 |
| --- | --- | --- |
| Issue 本文 | `運用区分` 欄を追加する | `目的 / 対象 / 受け入れ条件` のまま |
| Issue Form | dropdown を追加する | 追加しない |
| helper script | `--operation-mode` を追加する | 追加しない |
| workflow | 運用区分欄を強制する | 本文の最小項目と必須ラベルだけ見る |
| AI Agent | Issue 本文に項目を埋めさせる | 起票前プランで判定と理由を言わせる |

この方針では、各ファイルの役割を次のように分けました。

| ファイル | 役割 |
| --- | --- |
| `CONTRIBUTING.md` | 運用ルールの正本 |
| `docs/operations/github-flow-guardrails.md` | 採用理由、未採用案、将来の再検討条件 |
| `CLAUDE.md` | Claude Code が作業前に読む入口 |
| Issue template | `目的 / 対象 / 受け入れ条件` だけを保つ |
| workflow | 本文の最小項目と必須ラベルを検査する |

Issue を作るたびに新しい項目を埋めるのではなく、起票前のプランで「これは軽く進めてよいか、厳密に進めるべきか」を確認する形にしました。

## 運用コンテキスト

対象にしたリポジトリは、AWS / Terraform / GitHub Actions を扱う `terraform-hannibal` です。

<https://github.com/kmryst/terraform-hannibal>

前提は次の通りです。

- 個人開発または少人数運用
- 対象環境は `dev` 中心
- Issue / PR / CI を必須にしている
- `type / area / risk / cost` ラベルを Issue / PR に付けている
- Terraform / IAM / OIDC / GitHub Actions の変更は失敗時の影響が大きい
- AI Agent / CLI / API からも Issue / PR が作られる

このあたりの基本的な GitHub 運用は、以前の記事で書きました。

<https://zenn.dev/kmryst/articles/ai-agent-github-flow-guardrails>

今回の話は、その続きです。

「AI Agent が雑に Issue / PR を作っても壊れない」状態に近づくと、次に出てくるのは「どこまでルールを増やすべきか」という問題でした。

## きっかけ: Claude Code向けのCLAUDE.mdを追加した

まず、Claude Code がこのリポジトリで作業する前に読むファイルとして、リポジトリ直下に `CLAUDE.md` を追加しました。

実際に追加した PR はこれです。

<https://github.com/kmryst/terraform-hannibal/pull/141>

`CLAUDE.md` には、次のような内容をまとめています。

- 作業開始前に読むファイル
- Issue 駆動開発の順序
- Issue / PR 作成前に人間確認を挟むこと
- `scripts/github` の helper script を使うこと
- PR 必須ラベル
- 厳密運用に該当する変更
- Terraform / IAM / OIDC / GitHub Actions 変更時の注意
- 禁止事項
- ユーザー確認が必要な操作

これにより、Claude Code に毎回長いプロンプトを書かなくても、

```text
CLAUDE.md に従って Issue #xxx の範囲だけ作業して
```

くらいで進めやすくなりました。

ここまでは、素直にルールを明文化する話です。問題はその次でした。

## 論点: 軽運用 / 厳密運用をIssueにどう表すか

このリポジトリには、軽運用 / 厳密運用という考え方があります。

これは DevOps や ITIL の標準用語として使っているわけではなく、このリポジトリ内で作業フローを分けるための呼び名です。

端的に言うと、軽運用は docs や文言修正のような影響範囲の小さい変更です。厳密運用は Terraform、GitHub Actions、IAM / OIDC、Secrets、Network、Security、deploy / destroy、コスト影響、ロールバックを考える必要がある変更です。

厳密運用では、PR 本文の `ロールバック` 欄に実質的な内容を書く必要があります。

ここで最初に考えた案は、Issue 本文に `運用区分` のような項目を追加することでした。

たとえば、Issue に次のような欄を作る案です。

```md
## 運用区分

厳密運用

理由:
- terraform/** を変更する
- PR本文のロールバック必須
```

一見よさそうです。

Issue を見ただけで、軽運用か厳密運用か分かります。AI Agent にも判断を明示させられます。GitHub Issue Form に dropdown を追加することもできます。

でも、よく考えると違和感がありました。

## 違和感: それは本当にIssue本文に必要か

Issue 本文に `運用区分` を追加すると、たしかに情報は増えます。

しかし、その分だけ起票時の摩擦も増えます。

このリポジトリでは、Issue 本文の最小項目を次の3つに絞っています。

- `目的`
- `対象`
- `受け入れ条件`

ここに新しい必須項目を追加すると、軽微な docs 修正や小さな文言修正でも、毎回さらに1項目を埋めることになります。

人間だけならまだしも、AI Agent / CLI / API 経由の起票も混ざります。入力欄を増やすほど、次のような問題が出ます。

- Agent が項目を埋め忘れる
- 形式だけ埋めて中身が薄くなる
- Issue Form と CLI テンプレートと helper script の同期対象が増える
- workflow のチェック条件が増える
- 軽微な変更でも起票が重くなる

そして一番大きいのは、**運用区分は Issue 本文に保存したい情報というより、作業フローを選ぶための判断**だという点です。

判断したいのは、Issue 本文に「厳密運用」と書かれているかではありません。本当に必要なのは、次のような判断です。

- この変更は軽く進めてよいか
- PR 本文にロールバックが必要か
- Terraform / IAM / OIDC / GitHub Actions などの追加確認が必要か
- 人間確認を丁寧にすべきか

つまり、項目名を増やすよりも、**どこで判断するか**を決める方が重要でした。

## 採用した方針: Issue本文ではなく、起票前プランで判定する

最終的には、Issue 本文には新項目を追加しないことにしました。

代わりに、AI Agent を使う場合は、Issue 起票前プランに次を含めます。

- タイトル案
- `目的`
- `対象`
- `受け入れ条件`
- 推奨ラベル `type / area / risk / cost`
- 軽運用 / 厳密運用の判定と理由
- 使用ヘルパー

PR 作成前プランにも、軽運用 / 厳密運用の判定と理由を含めます。厳密運用の場合は、`ロールバック` が必須かどうかも明示します。

実際に `CONTRIBUTING.md` には、次のように書きました。

```md
AI Agent を使う場合は、いきなり起票せずに先に Issue プランを提示し、人間が確認してから起票します。
Issue プランには、少なくともタイトル案、`目的`、`対象`、`受け入れ条件`、推奨ラベルとしての `type/area/risk/cost`、軽運用 / 厳密運用の判定と理由、`使用ヘルパー: ./scripts/github/create-issue-with-labels.sh` を明示して含めてください。
Issue 本文には、専用の運用区分欄は追加しません。運用区分は、起票前プランと PR 作成前プランで確認します。
```

`CLAUDE.md` には、Claude Code が読む入口として短く書いています。

```md
Issue 作成前プランには、タイトル案、目的、対象、受け入れ条件、推奨ラベル、使用ヘルパー、軽運用 / 厳密運用の判定と理由を明示する。
Issue 本文には専用の運用区分欄を追加しない。
```

`docs/operations/github-flow-guardrails.md` には、なぜ本文項目にしないかを書きました。

```md
Issue 本文の必須項目を増やすと、軽微な docs / CI 修正や AI Agent / CLI 起票の負担が増えやすいため、運用区分は本文項目としては持たせません。
代わりに、人間または AI Agent が起票前プランでラベル・変更対象・変更内容を見て判断します。
```

これで、Issue 本文の必須項目は増やさずに、必要な判断だけは前段で行えます。

AI Agent には、たとえば起票前に次のように言わせます。

```text
運用モード: 厳密運用
理由:
- `.github/workflows/**` を変更するため
- OIDC を使う GitHub Actions の実行経路に関わるため
- PR本文のロールバック欄が必須
```

docs のみで軽い場合は、次のようになります。

```text
運用モード: 軽運用
理由:
- docs の文言修正のみ
- Terraform / GitHub Actions / IAM / Secrets / Network / Security に触れない
- コスト影響なし
```

これなら、人間は Issue 作成前に判断を確認できます。一方で、Issue 本文そのものはシンプルなままです。

## 厳密運用の条件は明文化する

Issue 本文に項目を増やさない代わりに、判定基準は曖昧にしないようにしました。

厳密運用に該当する条件は、次のように整理しています。

- `risk:medium` / `risk:high`
- `cost:medium` / `cost:large`
- `terraform/**`
- `.github/workflows/**`
- `scripts/deployment/**`
- `scripts/validation/**`
- IAM / OIDC / Permission Boundary
- Secrets / Network / Security
- deploy / destroy に関わる変更
- 運用環境に影響する変更
- コスト影響がある変更
- ロールバックを考える必要がある変更

軽運用は、これらに該当しない変更です。たとえば docs や README の文言修正、影響範囲が限定的な軽微修正などです。

ただし、docs のみの変更でも、IAM / OIDC / Secrets / Network / Security / deploy / destroy / コスト影響 / ロールバック方針に関わる場合は厳密運用として扱います。

`docs` だから軽いのではありません。**変更の内容が運用判断に関わるなら重く見る**、という方針です。

## 採用しなかった案

今回、採用しなかった案もあります。

### Issue本文に `運用区分` 欄を追加する

採用しませんでした。

理由は、Issue 本文の必須項目が増え、軽微な起票や AI / CLI 起票の負担が増えるためです。

運用区分は保存したい本文情報というより、作業フローを選ぶための判断です。そのため、本文項目ではなく起票前プランで扱うことにしました。

### GitHub Issue Form に dropdown を追加する

採用しませんでした。

Web UI からの起票には有効ですが、CLI / API / AI Agent 経由の起票には効きません。さらに、Issue Form と CLI テンプレートと helper script の同期対象が増えます。

今回は、入力欄を増やすより、起票前プランでの確認に寄せました。

### helper script に `--operation-mode` を追加する

採用しませんでした。

Issue 作成コマンドが長くなり、運用区分を本文やラベルにどう反映するかも決める必要があります。

現時点では、`type / area / risk / cost` ラベルと変更対象を見れば、軽運用 / 厳密運用の判定はできます。別引数を増やすより、正本ドキュメントで判断基準を明確にする方が軽いと判断しました。

### workflow で運用区分欄を強制する

採用しませんでした。

workflow の役割は、Issue 本文の最小項目と必須ラベルを検査することに留めました。運用区分まで CI で強制すると、Issue Form、CLI テンプレート、helper script、workflow の同期対象が増えます。

さらに、運用区分の誤検知は起票の失敗に直結します。軽微な変更を進めたいだけなのに、分類欄の不足や判定ミスで止まると、ガードレールではなく摩擦になります。

そのため、機械チェックは `目的 / 対象 / 受け入れ条件` と必須ラベルに集中させ、運用区分の判断は起票前プランと PR 作成前プランで人間が確認することにしました。

## 判断する場所を変える

今回の学びは、AI Agent を開発フローに組み込む時は、項目を増やすより、判断を言わせる方が効く場面があるということです。

運用ルールを作るとき、つい「漏れを防ぐには項目を増やせばよい」と考えがちです。

しかし、項目を増やすと、今度はそれ自体が運用負荷になります。特に AI Agent が入ると、次のような圧力が出ます。

- 忘れないようにテンプレート項目を追加する
- 判定を機械的に強制する
- helper script に引数を増やす
- workflow のチェックを増やす
- すべてを本文に残そうとする

もちろん、必要な場面では有効です。

ただし、すべてを Issue 本文や CI チェックに押し込むと、軽微な変更まで重くなります。日常的に守れないルールは、最終的には形骸化します。

今回の判断は、その逆です。

- 目的 / 対象 / 受け入れ条件は Issue 本文に残す
- `type / area / risk / cost` はラベルで管理する
- 軽運用 / 厳密運用の判定は起票前プランで行う
- 厳密運用なら PR でロールバックを書く
- 判断基準は `CONTRIBUTING.md` に集約する

項目を増やすのではなく、判断する場所を変えました。

## まとめ

AI Agent と一緒に開発運用を整えると、ルールを厚くしたくなります。

しかし、運用を安定させるために必要なのは、必ずしも項目を増やすことではありません。どの情報を本文に残し、どの判断を作業前プランで行い、どの条件を CI で強制するかを分けることが大事でした。

Issue 本文に新しい欄を増やさず、判断する場所を起票前プランと PR 作成前プランへ移す。

AI Agent を開発フローに組み込むほど、運用を重くしない判断も必要になります。
