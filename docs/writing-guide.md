# Zenn 技術記事を書くときのガイド

## このガイドの前提

このガイドは、インフラ / DevOps / AWS を主戦場にするエンジニアが、Zenn で技術記事を書くための個人用ガイドです。

汎用的な文章術ではなく、Terraform、GitHub Actions、CI/CD、IAM、OIDC、運用設計、障害対応、移行、改善判断のような記事を前提にしています。

そのため、rollback、blast radius、権限境界、運用コンテキスト、コスト影響、機密情報の扱いなど、インフラ / DevOps 記事で重要になる観点を重めに扱います。

フロントエンド、ライブラリ、アルゴリズム、OSS 貢献などの記事を書く場合も、対象読者、先に結論、選ばなかった選択肢、読者価値の考え方は使えます。ただし、DevOps / AWS 固有の項目は必要なものだけ拾います。

使うときは、まず「核にする考え方」と「書きすぎないこと」で記事の方向を決めます。次に記事タイプを選び、「本文で意識すること」の必須項目を満たします。最後に「公開前チェック」で漏れを確認します。

## 核にする考え方

技術記事は、完成形の正解だけを書くよりも、実装中にどこで詰まったか、そこからどう切り分けたか、解決策として何を選び、どの案を採用しなかったかまで書くと価値が出やすい。

記事の目的は、作業履歴をそのまま残すことではなく、読者が使える判断材料を残すこと。

作業報告を記事に変換するときは、次を先に決める。

- 読者はこの記事を読んだあと、何を判断できるようになるか
- 読者が自分の環境に持ち帰れる判断軸は何か
- リポジトリや PR のリンクを開かなくても、記事内だけで要点が伝わるか
- 自分の作業履歴ではなく、読者が再利用できる形に翻訳できているか

特に大事なのは「選ばなかった選択肢」を明示すること。

- 何を試したか
- どこで詰まったか
- どの案を採用しなかったか
- なぜ採用しなかったか
- 一時退避したなら、なぜ恒久策にしなかったか
- 最終的にどう戻したか

この判断の流れがあると、単なる手順メモではなく、同じ状況で迷っている人の意思決定に使える記事になる。

改善・移行を扱う記事では、改善前の状態に至った経緯も書く。「最初から最善策を取れなかったのはなぜか」「当時の判断は合理的だったか」を説明することで、読者は「自分が同じ判断をしたとき、次の手は何か」を考えられる。改善前の構成を批判するのではなく、当時の制約と選択の変遷として書くのがポイント。

比較や設計判断を扱う記事では、案を並べる前に評価軸を定義する。好みではなく判断基準で比較していることが伝わりやすくなる。評価軸は記事の文脈ごとに決める。たとえば運用設計なら `Operational Overhead`、可用性なら `Recoverability`、開発体験なら `Developer Experience` のように、その記事で本当に比較したい観点を置く。軸名は英語でもよいが、最初の1回だけ日本語を併記して意味を固定しておく。

また、比較表は1枚に詰め込まない方が読みやすいことが多い。採用した改善の段階比較と、採用しなかった案の比較は分ける。前者は評価軸に対して `High / Medium / Low` のように整理し、後者は `Strength / Limitation / Why Not Adopted` のように、トレードオフと不採用理由が見える形で並べると、設計判断の記録として強くなる。

ここでいうトレードオフとは、強制力を上げると運用負荷が増える、可用性を上げると一貫性が下がる、のように、ある利点の裏で別のコストや制約が増える関係を指す。

## 書きすぎないこと

- すべての前提知識を説明しようとしない
- 本筋に関係ない作業ログを全部貼らない
- 暫定策を、あたかも推奨構成のように書かない
- まだ検証していない改善案を、実施済みのように書かない
- 読者が欲しい判断材料より、自分の作業履歴を優先しない
- 記事の主張に必要ない一覧、ログ、設定全文は `:::details` に逃がすか削る

## 文体

- 「です/ます」調で統一する
- 一人称は使わないか、使うなら控えめにする
- 口語的な砕けた表現は、読者が共感しやすい場面（詰まった瞬間、勘違いの描写など）に限定して使う
- 技術的な説明部分では曖昧な表現を避け、断定できるところは断定する

## フロントマター

記事の中身より先にフロントマターを決める。Zenn のフロントマターは以下の5項目。

```yaml
---
title: ""
emoji: ""
type: "tech"
topics: []
published: false
---
```

- **title**: 結果や判断が伝わる表現にする。詳細は下記「タイトルの付け方」で扱う
- **emoji**: 記事の主題や雰囲気を端的に表すものを1つ選ぶ
- **type**: 技術的な実装・トラブルシュートなら `tech`、考え方やポエム寄りなら `idea`
- **topics**: 最大5つ。検索・発見性に直結するため、記事の主要技術をカバーするように選ぶ。略称や表記ゆれに注意（例: `githubactions` であって `github-actions` ではない）
- **published**: 下書き段階では `false` にしておき、公開前チェックを通してから `true` に変える

### タイトルの付け方

タイトルの先頭には「テーマ名」ではなく「痛み・変化・結果」を置く。読者がタイトルだけで「何が起きたか」「何が得られるか」を判断できることを目指す。

#### 原則

1. **先頭で「何の話か」を一発で伝える**: 技術名・ツール名はできるだけ早く出す
2. **結果が見える動詞を使う**: 「〜した」「〜変わった」「〜作った」「〜防げる」
3. **数字があるなら入れる**: 具体性と説得力が上がる（失敗率、件数、期間、コストなど）
4. **痛みや違和感をそのまま出す**: 読者が「自分のことだ」と感じる入口になる
5. **読者の得になる形にする**: 「〜できるようにした」「〜を取り戻す」「〜学べる」のように、読んだ先に何があるかを示す
6. **意外性や対立を入れる**: 消える／生まれる、覚えてる／学んでる のような対比は目を引く
7. **連載名・形式名は末尾に置く**: 先にクリック理由を出す
8. **抽象語から始めない**: 「進化録」「改善記」「設計メモ」「学習ログ」は意味は分かるがクリック理由にならない

#### パターン別の例

**痛み・問題型** — 読者の共感を入口にする:

- `CI/CDが安定しない人向け：失敗率76%からの設計`
- `「直す圧力」に気づいてから変わった、ポストモーテムへの向き合い方`

**変化・結果型** — 何がどう変わったかを示す:

- `全PRの83%をAIレビューだけでマージできるようにした`
- `Claude Codeのメモリを3階層にしたら「覚えてる」が「学んでる」に変わった`

**主張・意外性型** — 対比や逆説で引きつける:

- `脱CDKしてTerraformに移行すべきn個の理由`
- `S3 Filesで消えるアーキテクチャ層、生まれるアーキテクチャ`
- `SOLIDやクリーンアーキテクチャの前に「入力・処理・出力」を分けよう`

**実用・読者の得型** — 読者が得をする形で提示する:

- `【実験あり】axios攻撃は2行で防げる`
- `GitHub Copilot CLIを"タダ"で体系的に学べるコースをやってみた`

**弱い例（クリック理由が不足）:**

| 弱い例 | 改善例 |
| --- | --- |
| `GitHub Actions CI/CD進化録①` | `CI/CDが安定しない人向け：失敗率76%からの設計` |
| `CI/CD改善記①` | `GitHub Actionsの失敗を減らすために、まず通知より設計を見直した` |
| `Terraform設計メモ` | `TerraformのPR失敗をpre-commitで手前に寄せた` |
| `AWS学習ログ` | `GitHub ActionsにAWSキーを置くのをやめた：OIDC移行で長期クレデンシャルを0本にした` |

連載にするときも、まずは訴求を優先する。シリーズ名を入れるなら、主タイトルの後ろに補助情報として足す。

## 基本構成

記事のタイプによって骨格を使い分ける。

実際の記事は、複数の型が混ざることが多い。移行記事の中でトラブルシュートが起きたり、実装記事の中盤で設計比較が必要になったりする。その場合でも、主軸の型を1つ決める。副論点は独立した見出しに分け、記事全体の流れを壊さない位置に置く。

### トラブルシュート・実装型

問題発生 → 原因特定 → 一時的解決 → 根本解決の順にすると、読者が思考プロセスを追いやすい。

1. 何をやりたかったか
2. なぜそれをやりたかったか
3. 先に結論（最終的な着地点を先に見せる）
4. どこで詰まったか
5. 最初に疑ったこと
6. 実際の原因
7. 一度選んだ暫定策
8. その暫定策を恒久策にしなかった理由
9. 本命構成に戻した方法
10. 採用しなかった選択肢とその理由
11. 学び
12. 次に改善するなら何か

### 設計解説型

設計意図と制約条件を先に出し、構成の詳細はその後で展開する。

1. 何を設計したか（全体像）
2. 設計上の制約・前提
3. 運用コンテキスト
4. 先に結論（最終的な構成を先に見せる）
5. 選んだ構成とその理由
6. 選ばなかった構成とその理由
7. 実装のポイント
8. 運用してみてわかったこと
9. 今後の改善

インフラ / DevOps の設計記事では、運用コンテキストとして少なくとも次を明示する。

- チーム規模
- 誰が実行するか
- 対象環境が `dev / staging / prod` のどれか
- 変更失敗時の影響範囲
- 権限境界

同じ構成でも、少人数の個人開発、共有の本番環境、権限分離の有無で評価は変わる。DevOps 記事では、この前提を抜くと設計判断の有効範囲が曖昧になりやすい。

### 比較・選定型

選択肢を並べて、判断基準と結論を明示する。

1. 何を比較・選定したか
2. 比較の背景と制約
3. 先に結論（何を選んだかを先に見せる）
4. 候補の一覧と特徴
5. 評価基準
6. 選んだものとその理由
7. 選ばなかったものとその理由
8. 導入後の所感・注意点

比較表を置く場合は、評価基準を本文で先に定義したうえで、表の役割も分ける。採用した案の比較表は評価軸中心、不採用案の比較表は `Strength / Limitation / Why Not Adopted` 中心、のように役割を分けると読みやすい。

### 移行・リファクタリング型

既存の構成を別の構成に置き換える記事。「なぜ移行前の構成になっていたか」の経緯を出すのが、他の型との大きな違い。

1. 前提条件・制約（`:::message` で冒頭に置く）
2. 運用コンテキスト（誰が、どの環境で、どの権限で運用しているか）
3. 先に結論（移行前後のフロー・変化した数値）
4. 用語の整理（移行先の技術に固有の用語を定義する）
5. なぜ移行前の構成になっていたか（経緯・変遷）
6. 何が課題になったか
7. やったこと（手順・コマンド例）
8. 選ばなかった選択肢とその理由
9. 検証（移行後の動作確認）
10. 学び
11. 今後の改善・残課題

## 本文で意識すること

### 必須: 記事の骨格

- 冒頭か序盤で対象読者を明示する
- 初出の専門用語は一言で定義する
- 独自用語やプロジェクト固有の呼び名は、初出時に「一般用語ではなくこの記事内の呼び名」であることも含めて定義する
- 「先に結論」を置いて、読者が全体像をつかめるようにする
- 制限事項や前提条件は記事の後半にまとめず、序盤（冒頭の `:::message` や「先に結論」の直後）で触れる
- 複数の論点を1つのセクションに混在させない。論点が変わったら見出しを分ける
- 最後に「学び」「まとめ」「今後の改善」を置き、読後に何が残るかを整理する
- まとめでは「先に結論」の箇条書きをそのまま繰り返さず、記事全体から得られる判断や意味づけを短く残す

### 必須: 読者価値

- 作業履歴ではなく、読者が使える判断材料にする
- 実装中に何を優先し、どこで妥協したかの判断基準を書く
- 一時的な workaround と恒久策を混ぜない
- 選んだ案だけでなく、選ばなかった案を書く
- 不採用理由は感情的な「捨てた」「却下した」ではなく、制約とトレードオフの不一致として書く
- 「先に結論」の直後に、必要なら before / after 表や変更前後の比較を置く。読者が記事全体の地図として使えるようにする
- ファイル、サービス、コンポーネントなど登場人物が複数ある記事では、役割表を早めに置く
- リポジトリや PR のリンクを開かなくても要点が伝わるように、必要な差分や設定の抜粋を記事内に置く
- 未完了の部分や今後の改善を正直に書く

### 設計・比較・移行記事で重要

- 実装の制約、運用の制約、権限の制約を分けて説明する
- 比較表を使う場合は、各列が何を意味するかを本文で一度定義する
- 採用した案と採用しなかった案を、同じ表に無理に押し込めない
- 定量的な成果（実行時間、コスト、失敗率など）は、具体的な数値で示す
- 定量指標を書く場合は、何を指標にしたか、どこから取った数値か、before / after をどう比較したかまで明示する
- 「現時点では使っていないが将来の拡張を見越した選択」をしている場合は、その意図を明示する

### インフラ / DevOps / AWS 記事で重要

- チーム規模、実行者、対象環境、権限境界などの運用コンテキストを早い段階で明示する
- 失敗時にどう止まり、どう戻せるかを書く。rollback、recoverability、blast radius、failure mode、誤検知時の運用などを必要に応じて扱う
- IAM / OIDC / Permission Boundary / Secrets / Network / Security / コスト影響に関わる場合は、権限と影響範囲を明示する
- クラウドサービスの仕様を記述する場合、時点と現時点の挙動を具体的に示す
- 「公式ドキュメントを確認してください」だけで終わらせず、「いつから」「何が変わったか」「今どういう挙動になっているか」を明記し、参照先 URL を添える
- AWS 公式ドキュメントなど、読者が確認できる一次情報へのリンクを置く

### 公開前確認に回すもの

- コード例だけでなく、診断や復旧に使うコマンド例も入っているか
- エラーメッセージやログは、原因特定に必要な要点だけに絞れているか
- ツールやライブラリのコマンド名、deprecated、対象バージョンを、公式ドキュメント・リリースノート・実際の設定ファイルで確認したか
- コマンド出力や設定例に AWS アカウント ID、ARN、アクセスキー、エンドポイント URL などの機密情報が残っていないか

## コードブロックの書き方

- 言語指定を必ず付ける（`hcl`, `bash`, `text`, `yaml` など）
- 変更前後を示す場合は `diff` 表記か、コメントで Before / After を明示する
- 1ブロックは読者がスクロールせずに把握できる長さ（目安20行以内）に収める。超える場合は分割するか要点を抜粋する
- コードだけで文脈が伝わらない場合は、直前に1文で目的を書く
- **コマンド出力・設定例に機密情報が含まれていないか必ず確認する**: AWS アカウント ID、ARN 内のアカウント ID、アクセスキー、エンドポイント URL など。マスクは記事全体で一貫した表記（`xxxx` や `xxxxxxxxxxxx` など）で統一する。設定例では `xxxx` でも確認用の実行出力では実 ID が混入しやすいため注意する

## 図・スクリーンショットの使い方

文章やコードだけで関係性を追うのが難しい場合は、図を使う。

- アーキテクチャ、ネットワーク、権限境界、CI/CD フローは図が効きやすい
- 移行や改善の記事では before / after 図があると変化が伝わりやすい
- UI の状態や設定画面を示す必要がある場合はスクリーンショットを使う
- コードや差分で正確に示せるものを、無理にスクリーンショットにしない
- 図には主張に必要な要素だけを入れ、サービス名や矢印を詰め込みすぎない
- 画像内にアカウント ID、ARN、URL、ユーザー名、リソース名など公開したくない情報が残っていないか確認する

## 記事の長さ

長さは目的で決める。目安として、実装や設計判断を扱う記事は 3,000〜8,000 字に収まると読みやすい。

- 2,000 字未満の場合は、判断材料、前提、選ばなかった案が不足していないか確認する
- 8,000 字を超える場合は、読者が途中で迷わないように構成表、before / after、見出しを強くする
- 10,000 字を超える場合は、記事を分けるか、補足資料を `:::details` に逃がすことを検討する
- 1記事で扱う主張は原則1つにする。複数の主張が同じ重さで並ぶなら分割候補にする

## Zenn 記法の活用

Zenn 固有のマークダウン拡張を適切に使い、本文の可読性を上げる。

- `:::message` — 補足情報や前提条件の強調に使う
- `:::message alert` — 読者が見落とすと困る警告・注意事項に使う
- `:::details タイトル` — 長いエラーログ、全文のコード、補助的な説明など、本筋を読むのに必須ではない内容を折りたたむ

本文の流れを止めずに情報量を確保したいときに有効。ただし、記事の核心部分を折りたたみの中に隠さない。

判定条件や長い一覧は、本文の論旨に必要なら通常の本文として出す。補足資料としてあれば十分な場合だけ `:::details` に入れる。

たとえば、記事の主張が「どこで判断するか」なら、判断基準の一覧は本文に置いてもよい。記事の主張が別にあり、一覧が参照資料に近いなら折りたたむ。

## AI Agentレビューの使い方

公開前に Claude Code や Codex へレビューさせる場合は、修正まで任せず、まずレビューだけにする。

レビュー依頼では、次を明示する。

- 対象読者
- 記事で届けたい価値
- レビューだけで修正は禁止すること
- 指摘してほしい観点

特に見てもらう観点は次。

- 読者がこの記事から何を持ち帰れるか
- 作業報告に寄りすぎていないか
- 初出の用語や独自概念が説明されているか
- 具体例、差分、抜粋が不足していないか
- 同じ主張を複数回繰り返していないか
- 採用しなかった案の理由が循環していないか
- 「まとめ」が「先に結論」の焼き直しになっていないか

レビュー結果を反映するときは、すべてを機械的に採用しない。記事の対象読者と主張に照らして、読者価値が増える指摘だけを採用する。

## 公開前チェック

### メタデータ・体裁

- title の先頭で「痛み・変化・結果」のいずれかを出せているか
- title に技術名・ツール名が含まれているか
- title に数字を入れられる内容なのに省略していないか
- title が「進化録」「改善記」「設計メモ」のような抽象語だけで弱くなっていないか
- title に結果が見える動詞（〜した、〜できるようにした、〜防げる）があるか
- title から読者の得（読んだら何がわかるか）が伝わるか
- topics が記事の主要技術をカバーしているか（最大5つ）
- emoji が記事の主題に合っているか
- 文体が「です/ます」調で統一されているか
- コードブロックに言語指定が付いているか
- `:::message` や `:::details` を使うべき箇所を見落としていないか
- コマンド出力・設定例に AWS アカウント ID など機密情報が残っていないか（設定例でマスクしていても、確認コマンドの出力で実値が混入しやすい）

### 内容

- 初出の専門用語を一言で定義しているか
- 独自用語やプロジェクト固有の呼び名を、一般用語と誤解されないように定義しているか
- 対象読者を明示しているか
- 「先に結論」があるか
- 序盤に before / after 表、役割表、構成図など、記事全体の地図になる情報があるか
- リンク先を開かなくても、記事内に必要な差分や設定の抜粋があるか
- 読者が再現・診断できるコマンド例があるか
- エラーメッセージやログの要点があるか
- 「何を選んだか」だけでなく「何を選ばなかったか」があるか
- 制約とトレードオフの観点で、なぜ採用しなかったかが書けているか
- 不採用理由が「採用しなかったから採用しない」のような循環になっていないか
- 暫定策と恒久策の違いが伝わるか
- 改善・移行系の記事の場合、改善前の構成に至った経緯（当時の制約と判断）が書けているか
- 複数の問題を扱う場合、それぞれが見出しで分離されているか
- 判断基準や妥協点が書けているか
- 公式ドキュメントや一次情報へのリンクがあるか
- 運用コンテキスト（チーム規模、実行者、対象環境、権限境界）が序盤で明示されているか
- 数値を出している場合、その観測元と比較条件が書けているか
- rollback、blast radius、failure mode など、失敗時の扱いが必要な記事で落ちていないか
- コマンド名・オプション・deprecated の有無を、対象バージョンの公式ドキュメントや実際の設定ファイルで確認したか
- 記事の最後に、今回のスコープ外にした改善が残っているか
- まとめが「先に結論」の繰り返しではなく、読者に残したい判断や意味づけで締まっているか
