# Zenn 技術記事を書くときのガイド

## 核にする考え方

技術記事は、完成形の正解だけを書くよりも、実装中にどこで詰まったか、そこからどう切り分けたか、解決策として何を選び、何を捨てたかまで書くと価値が出やすい。

記事の目的は、作業履歴をそのまま残すことではなく、読者が使える判断材料を残すこと。

特に大事なのは「選ばなかった選択肢」を明示すること。

- 何を試したか
- どこで詰まったか
- どの案を捨てたか
- なぜ捨てたか
- 一時退避したなら、なぜ恒久策にしなかったか
- 最終的にどう戻したか

この判断の流れがあると、単なる手順メモではなく、同じ状況で迷っている人の意思決定に使える記事になる。

改善・移行を扱う記事では、改善前の状態に至った経緯も書く。「最初から最善策を取れなかったのはなぜか」「当時の判断は合理的だったか」を説明することで、読者は「自分が同じ判断をしたとき、次の手は何か」を考えられる。改善前の構成を批判するのではなく、当時の制約と選択の変遷として書くのがポイント。

## 文体

- 「です/ます」調で統一する
- 一人称は使わないか、使うなら控えめにする
- 口語的な砕けた表現は、読者が共感しやすい場面（詰まった瞬間、勘違いの描写など）に限定して使う
- 技術的な説明部分では曖昧な表現を避け、断定できるところは断定する

## フロントマター

記事の中身より先にフロントマターを決める。Zenn のフロントマターは以下の5項目。

```yaml
---
title: ""
emoji: ""
type: "tech"
topics: []
published: false
---
```

- **title**: 結果や判断が伝わる表現にする。詳細は下記「タイトルの付け方」で扱う
- **emoji**: 記事の主題や雰囲気を端的に表すものを1つ選ぶ
- **type**: 技術的な実装・トラブルシュートなら `tech`、考え方やポエム寄りなら `idea`
- **topics**: 最大5つ。検索・発見性に直結するため、記事の主要技術をカバーするように選ぶ。略称や表記ゆれに注意（例: `githubactions` であって `github-actions` ではない）
- **published**: 下書き段階では `false` にしておき、公開前チェックを通してから `true` に変える

### タイトルの付け方

タイトルの先頭には「テーマ名」ではなく「痛み・変化・結果」を置く。読者がタイトルだけで「何が起きたか」「何が得られるか」を判断できることを目指す。

#### 原則

1. **先頭で「何の話か」を一発で伝える**: 技術名・ツール名はできるだけ早く出す
2. **結果が見える動詞を使う**: 「〜した」「〜変わった」「〜作った」「〜防げる」
3. **数字があるなら入れる**: 具体性と説得力が上がる（失敗率、件数、期間、コストなど）
4. **痛みや違和感をそのまま出す**: 読者が「自分のことだ」と感じる入口になる
5. **読者の得になる形にする**: 「〜できるようにした」「〜を取り戻す」「〜学べる」のように、読んだ先に何があるかを示す
6. **意外性や対立を入れる**: 消える／生まれる、覚えてる／学んでる のような対比は目を引く
7. **連載名・形式名は末尾に置く**: 先にクリック理由を出す
8. **抽象語から始めない**: 「進化録」「改善記」「設計メモ」「学習ログ」は意味は分かるがクリック理由にならない

#### パターン別の例

**痛み・問題型** — 読者の共感を入口にする:

- `CI/CDが安定しない人向け：失敗率76%からの設計`
- `「直す圧力」に気づいてから変わった、ポストモーテムへの向き合い方`

**変化・結果型** — 何がどう変わったかを示す:

- `全PRの83%をAIレビューだけでマージできるようにした`
- `Claude Codeのメモリを3階層にしたら「覚えてる」が「学んでる」に変わった`

**主張・意外性型** — 対比や逆説で引きつける:

- `脱CDKしてTerraformに移行すべきn個の理由`
- `S3 Filesで消えるアーキテクチャ層、生まれるアーキテクチャ`
- `SOLIDやクリーンアーキテクチャの前に「入力・処理・出力」を分けよう`

**実用・読者の得型** — 読者が得をする形で提示する:

- `【実験あり】axios攻撃は2行で防げる`
- `GitHub Copilot CLIを"タダ"で体系的に学べるコースをやってみた`

**弱い例（クリック理由が不足）:**

- `GitHub Actions CI/CD進化録①`
- `CI/CD改善記①`
- `Terraform設計メモ`
- `AWS学習ログ`

連載にするときも、まずは訴求を優先する。シリーズ名を入れるなら、主タイトルの後ろに補助情報として足す。

## 基本構成

記事のタイプによって骨格を使い分ける。

### トラブルシュート・実装型

問題発生 → 原因特定 → 一時的解決 → 根本解決の順にすると、読者が思考プロセスを追いやすい。

1. 何をやりたかったか
2. なぜそれをやりたかったか
3. 先に結論（最終的な着地点を先に見せる）
4. どこで詰まったか
5. 最初に疑ったこと
6. 実際の原因
7. 一度選んだ暫定策
8. その暫定策を恒久策にしなかった理由
9. 本命構成に戻した方法
10. 捨てた選択肢とその理由
11. 学び
12. 次に改善するなら何か

### 設計解説型

設計意図と制約条件を先に出し、構成の詳細はその後で展開する。

1. 何を設計したか（全体像）
2. 設計上の制約・前提
3. 先に結論（最終的な構成を先に見せる）
4. 選んだ構成とその理由
5. 選ばなかった構成とその理由
6. 実装のポイント
7. 運用してみてわかったこと
8. 今後の改善

### 比較・選定型

選択肢を並べて、判断基準と結論を明示する。

1. 何を比較・選定したか
2. 比較の背景と制約
3. 先に結論（何を選んだかを先に見せる）
4. 候補の一覧と特徴
5. 評価基準
6. 選んだものとその理由
7. 選ばなかったものとその理由
8. 導入後の所感・注意点

### 移行・リファクタリング型

既存の構成を別の構成に置き換える記事。「なぜ移行前の構成になっていたか」の経緯を出すのが、他の型との大きな違い。

1. 前提条件・制約（`:::message` で冒頭に置く）
2. 先に結論（移行前後のフロー・変化した数値）
3. 用語の整理（移行先の技術に固有の用語を定義する）
4. なぜ移行前の構成になっていたか（経緯・変遷）
5. 何が課題になったか
6. やったこと（手順・コマンド例）
7. 選ばなかった選択肢とその理由
8. 検証（移行後の動作確認）
9. 学び
10. 今後の改善・残課題

## 本文で意識すること

- 冒頭か序盤で対象読者を明示する
- 初出の専門用語は一言で定義する
- 「先に結論」を置いて、読者が全体像をつかめるようにする
- 複数の論点を1つのセクションに混在させない。論点が変わったら見出しを分ける
- 実装の制約、運用の制約、権限の制約を分けて説明する
- 一時的な workaround と恒久策を混ぜない
- 実装中に何を優先し、どこで妥協したかの判断基準を書く
- 未完了の部分や今後の改善を正直に書く
- **「現時点では使っていないが将来の拡張を見越した選択」をしている場合は、その意図を明示する**: 現状の値や条件だけを見ると別の方法でも等価に見える場合（例：ワイルドカードを使わない `StringLike`）、なぜその選択をしたかを一文添えないと読者が「誤りでは？」と疑う原因になる
- **クラウドサービスの仕様を記述する場合、時点と現時点の挙動を具体的に示す**: 「公式ドキュメントを確認してください」だけでは読者が次の行動を取りにくい。「いつから」「何が変わったか」「今どういう挙動になっているか」を明記し、参照先 URL を添えること
- コード例だけでなく、診断や復旧に使うコマンド例も入れる
- エラーメッセージやログは、原因特定に必要な要点だけ載せる
- AWS 公式ドキュメントなど、読者が確認できる一次情報へのリンクを置く
- 最後に「学び」「まとめ」「今後の改善」を置き、読後に何が残るかを整理する
- 制限事項や前提条件は記事の後半にまとめず、序盤（冒頭の `:::message` や「先に結論」の直後）で触れておく。読者は最後まで読んでくれるとは限らない
- 定量的な成果（実行時間、コスト、失敗率など）は、具体的な数値で示す。定性的な表現だけでは説得力が弱い

## コードブロックの書き方

- 言語指定を必ず付ける（`hcl`, `bash`, `text`, `yaml` など）
- 変更前後を示す場合は `diff` 表記か、コメントで Before / After を明示する
- 1ブロックは読者がスクロールせずに把握できる長さ（目安20行以内）に収める。超える場合は分割するか要点を抜粋する
- コードだけで文脈が伝わらない場合は、直前に1文で目的を書く
- **コマンド出力・設定例に機密情報が含まれていないか必ず確認する**: AWS アカウント ID、ARN 内のアカウント ID、アクセスキー、エンドポイント URL など。マスクは記事全体で一貫した表記（`xxxx` や `xxxxxxxxxxxx` など）で統一する。設定例では `xxxx` でも確認用の実行出力では実 ID が混入しやすいため注意する

## Zenn 記法の活用

Zenn 固有のマークダウン拡張を適切に使い、本文の可読性を上げる。

- `:::message` — 補足情報や前提条件の強調に使う
- `:::message alert` — 読者が見落とすと困る警告・注意事項に使う
- `:::details タイトル` — 長いエラーログ、全文のコード、補助的な説明など、本筋を読むのに必須ではない内容を折りたたむ

本文の流れを止めずに情報量を確保したいときに有効。ただし、記事の核心部分を折りたたみの中に隠さない。

## 書きすぎないこと

- すべての前提知識を説明しようとしない
- 本筋に関係ない作業ログを全部貼らない
- 暫定策を、あたかも推奨構成のように書かない
- まだ検証していない改善案を、実施済みのように書かない
- 読者が欲しい判断材料より、自分の作業履歴を優先しない

## 公開前チェック

### メタデータ・体裁

- title の先頭で「痛み・変化・結果」のいずれかを出せているか
- title に技術名・ツール名が含まれているか
- title に数字を入れられる内容なのに省略していないか
- title が「進化録」「改善記」「設計メモ」のような抽象語だけで弱くなっていないか
- title に結果が見える動詞（〜した、〜できるようにした、〜防げる）があるか
- title から読者の得（読んだら何がわかるか）が伝わるか
- topics が記事の主要技術をカバーしているか（最大5つ）
- emoji が記事の主題に合っているか
- 文体が「です/ます」調で統一されているか
- コードブロックに言語指定が付いているか
- `:::message` や `:::details` を使うべき箇所を見落としていないか
- コマンド出力・設定例に AWS アカウント ID など機密情報が残っていないか（設定例でマスクしていても、確認コマンドの出力で実値が混入しやすい）

### 内容

- 初出の専門用語を一言で定義しているか
- 対象読者を明示しているか
- 「先に結論」があるか
- 読者が再現・診断できるコマンド例があるか
- エラーメッセージやログの要点があるか
- 「何を選んだか」だけでなく「何を選ばなかったか」があるか
- 「なぜ捨てたか」が書けているか
- 暫定策と恒久策の違いが伝わるか
- 改善・移行系の記事の場合、改善前の構成に至った経緯（当時の制約と判断）が書けているか
- 複数の問題を扱う場合、それぞれが見出しで分離されているか
- 判断基準や妥協点が書けているか
- 公式ドキュメントや一次情報へのリンクがあるか
- 記事の最後に、今回のスコープ外にした改善が残っているか
